## 1. 现状盘点：你手里真正有什么

### 1.1 硬指标（2026-09-18 实测）

| 项 | 数值 |
|---|---|
| 库 / 表 | **7 个库 / 46 张表**（源 11 + ODS 11 + DWD 13 + DWS 5 + ADS 6） |
| 源库数据量 | **约 270 万行**（订单 100 万 / 工单 50 万 / 成本凭证 50 万 / 出入库 49.2 万 / 库存快照 20 万） |
| 库体积 | 合计约 **5 GB**（dwd 1.29 GB > erp 0.94 GB > ads 0.79 GB） |
| ADS 最大表 | `ads_sale_analysis` **852,421 行** |
| ETL 单次耗时 | 约 **15 分钟**（step03 222s / step04 290s / step05 400s） |
| 代码量 | 6 个 Python 脚本 **2542 行**；ETL SQL **1181 行**；分层 DDL 46 份 |
| 数据校验 | `verify_data.py` **19 项断言**，实测 **19/19 通过** |
| 版本控制 | **18 commits，全部本地，无 git remote**；git 跟踪 73 个文件 |

### 1.2 可以写进简历的真实亮点（≥6 条，且都有代码/文档支撑）

1. **完整五层分层建模**：源库 → ODS（贴源 + 水位）→ DWD（6 维 + 6 事实）→ DWS（日/月双粒度）→ ADS（6 张面向看板的宽表）。分层边界清晰，不是"一张大表跑到底"。
2. **增量同步机制**：ODS 层用 `etl_watermark` 水位表 + `update_time` 过滤 + `ON DUPLICATE KEY UPDATE` UPSERT，**可重复执行、失败不推进水位、从断点续跑**。这是很多人练手项目里没有的东西。
3. **可执行的数据质量断言**：把文档里的"对答案"变成 19 项断言，分**规模 / 跨层对账（DWD=DWS=ADS，容差 0.1%）/ 一致性**三类，并**接入调度器——校验不过则整批算失败**。这一条是项目里最像生产环境的设计。
4. **口径治理有据可查**：`docs/PROJECT_MEMORY.md` 记录 **12 条口径决策**（为什么这么定、为什么不是别的定法），例如"营收剔除已取消/已作废订单（原口径虚高 20%）""订单履约率分母改为已交付（原口径把 17 万未发货单算作不按时）"。**这在简历项目里非常罕见**，是面试时最容易被追问、也最容易加分的部分。
5. **有真实故障复盘**：一次 `table is full` 爆盘事故的**双重根因分析**（binlog 堆积 + 巨型事务 + ODS 翻倍）与处置（`COMMIT_PER_STATEMENT`、`step00_ods_full_reset.sql`、Purge binlog）。**这是能讲 5 分钟的 STAR 素材**。
6. **分析结论有交付**：Jupyter 做客户 RFM 分层、车间"产能 × 良率"四象限，7 张 FineBI 看板落地。

### 1.3 不该写的（会在面试翻车）

- ❌ 不要写"千万级数据量""高并发""实时数仓"——实际是约 270 万行、单机 MySQL、T+1 全量重算。
- ❌ 不要写"独立设计实时链路"——目前 ODS 以上全是全量重建，没有实时组件。
- ❌ 不要把 `verify_data.py` 说成"数据质量平台"——它是 19 条硬编码断言的脚本，不是规则引擎。

## 3. 薄弱环节清单（按"面试杀伤力"从高到低）

> 每条给出：**现状（实测）→ 面试官会怎么问 → 改进方向 → 成本**

### 🔴 W1. 增量链路只做到 ODS，DWD 起全部全量重算（最大硬伤）

- **现状**：`step03/04/05` 开头都是 `TRUNCATE` + 全量 INSERT，重跑一次要 15 分钟；只有 `step01` 是增量的。
- **面试必问**："上游每天新增 500 万行，你还敢全量重算吗？讲一下你的增量方案。"
- **后果**：从"会分层"掉档成"只会跑 demo"，因为**增量是数仓工程的入门线**。
- **改进**：DWD 事实表按业务日期做**分区 + 按日增量写入**（`DELETE` 目标日分区 → `INSERT` 增量窗口）；DWS 改滚动累加（按天幂等重算 N 天窗口）；ADS 保持全量（量小）。
- **成本**：3~5 天。**优先级最高。**

### 🔴 W2. 没有任何分区表

- **现状**：46 张表 **0 张分区**，全靠普通索引 + 主键。
- **面试必问**："`dwd_sale_order_detail` 有 97 万行，如果到 10 亿行你的查询和归档怎么做？"
- **改进**：事实表按 `order_date` / `io_date` / `plan_start_date` 做 `RANGE PARTITION`（按月），并演示**分区裁剪**效果（`EXPLAIN` 前后对比）。
- **成本**：1~2 天（含重建表 + 重跑 ETL 验证）。

### 🟠 W3. 维度层没有代理键，也没有 SCD/拉链表

- **现状**：维度表主键就是业务自然键（`customer_id`），每天 `TRUNCATE` 重建，**无代理键、无生效/失效时间、无版本**。
- **面试必问**："客户改了名字/改了区域，历史订单关联到哪个名字？"
- **后果**：这是数仓建模的"送分题"，答不上来会显得只做过 ODS/ETL 没做过建模。
- **改进**：至少对 `dim_customer` / `dim_product` 建**拉链表**（`start_date / end_date / is_current` + `ROW_NUMBER` 比对变更），并在 README 里说明为什么小维度选 SCD1、客户维度选 SCD2。
- **成本**：2~3 天，收益很高（写进简历是"维度建模"的硬证据）。

### 🟠 W4. `TRUNCATE` 破坏原子性（已在文档里承认，但没修）

- **现状**：`TRUNCATE` 隐式提交 + 逐条提交 → 步骤中途失败会留下**空表**（第三轮事故后 DWD 曾全空）。
- **面试必问**："你的事务边界怎么设计的？中途失败数据是什么状态？"
- **改进**：改成"写入 `xxx_tmp` → 校验行数 → `RENAME TABLE` 原子切换"（或 `EXCHANGE PARTITION`）。
- **成本**：1 天。**小成本、高说服力**——一个"我知道问题在哪并且修了"的答案远胜于"我知道但没做"。

### 🟠 W5. 没有编排、没有补数、告警是假的

- **现状**：调度靠 `schedule` 库 + `--once` 手动跑；无 DAG 依赖、无重跑某天/区间的能力、失败告警只是 `logger.error`（邮件函数是空壳）。
- **面试必问**："任务失败了怎么重跑某一天？上游表没到位怎么办？"
- **改进**：换 **Airflow / DolphinScheduler**（本项目规模用任一个都行），至少做到：① 按日期参数化的 DAG；② 失败重跑指定日期；③ 企业微信/钉钉 Webhook 真告警。
- **成本**：3~5 天。

### 🟡 W6. 工程化几乎为零

- **现状**：**无 Dockerfile、无 docker-compose、无 CI、无单测、无依赖锁**（`requirements.txt` 10 条全是 `>=`）。
- **面试必问**："别人怎么在 5 分钟内把你这个环境跑起来？"
- **改进**：`docker compose up` 一键起 MySQL 8 + 初始化 46 张表 + 跑 ETL；GitHub Actions 跑 `build_init_sql.py --check` + `verify_data.py`；对 `_stable_ratio` / `split_cost` / `classify_quadrant` 等纯函数写 `pytest`。
- **成本**：2~3 天。

### 🟡 W7. 交付物不可见 —— 简历上给不出可点开的证据

- **现状**：**无 git remote**（18 commits 全在本地）→ 简历写不了 GitHub 链接；`bl/*.pdf`（7 份看板导出）被 `.gitignore` 排除 → 别人 clone 看不到看板；`README.md` **无任何截图**。
- **后果**：HR/面试官只能"听你说"，项目的视觉冲击力全部浪费。
- **改进**：建远程仓库（至少公开只读）；把 3~5 张看板截图（或 PDF）纳入版本控制；README 首屏放**架构图 + 看板截图 + 量级/耗时指标表**。
- **成本**：**半天**。**ROI 最高，先做这个。**

### 🟡 W8. 数据是"死"的，看板停在 3 个月前

- **现状**：大屏最后一天 **2026-06-29**，销售/工单/成本都停在 2026-06；今天 09-18，**7~9 月是空洞**。成本凭证仍停在 2026-06（这是有意设计，但 7~8 月的销售/生产空白不是）。
- **后果**：面试官点开截图，看到"最新日期是三个月前"，第一印象直接掉档。
- **改进**：`python scripts\generate_incremental_data.py 2026-07-01 2026-09-18` → 重跑 ETL → 更新看板截图。
- **成本**：**1 小时（含跑批）**。和 W7 一起做。

### 🟡 W9. 口径常量双份定义，没有指标字典

- **现状**：`UNIT_COST_MIN / MARGIN_MIN / COST_MIX / PLAN_QTY_MIN` 等口径常量在 `generate_fake_data.py` 与 `generate_incremental_data.py` **各写一份**，改一处必然漂移；无 `config/`。
- **面试必问**："同一个指标在多个脚本里怎么保证口径一致？"
- **改进**：抽 `dwh_config.py`（或 `config/metrics.yaml`）单点定义；把 `PROJECT_MEMORY.md §3` 的 12 条口径决策整理成 **`docs/metric_dictionary.md`**（指标名 / 业务定义 / 计算公式 / 数据来源 / 分母保护 / 责任人）。
- **成本**：1~2 天。指标字典是数仓岗的"专业感"加分项。

### 🟢 W10. 技术栈单一（纯单机 MySQL）

- **现状**：全链路只有 MySQL 8；ODS 以上无 OLAP 引擎、无 CDC、无消息队列。
- **说明**：**不建议无脑补**。只有在投递"湖仓一体 / 实时数仓"类岗位时才值得做。
- **改进（择一，不要全上）**：① ADS 换 **Doris / ClickHouse**，对比查询耗时（有真实收益，好讲）；② **Flink CDC / Maxwell** 把 ODS 同步改成实时（替换水位表轮询）；③ Hive/Spark 做 DWD 层以体现大数据栈。
- **成本**：每个 5~10 天。

### 🟢 W11. 分析结论没有回流数仓

- **现状**：RFM 分层、四象限结果只存在于 Notebook 和 PNG，**没有落成 ADS 表**，业务方（看板用户）看不到。
- **改进**：新增 `ads_customer_rfm` / `ads_workshop_quadrant` 两张 ADS 表，Notebook 逻辑改写成 `step06_ads_analysis.sql`，图表改由 FineBI 呈现。
- **成本**：2 天。收益是"分析→数仓→看板"闭环，故事更完整。

### 🟢 W12. 数据保留与运维

- **现状**：ODS 永久保留全量镜像（486 MB，未来持续增长）；源库物理删除**不会传播**到 ODS（已在 `step01` 注释里承认）；`binlog_expire_logs_seconds` 仍是 30 天（**重启已还原**），binlog 堆到 **4,687 MB**，C 盘仅剩 **21 GB**。
- **改进**：加 ODS 数据保留策略（如保留 N 天）；把 binlog 参数写进 `my.ini` 或直接 `skip-log-bin`；`datadir` 迁到 D 盘。
- **成本**：半天，但属于"运维成熟度"的加分项（能在面试里讲"我识别并消除了磁盘这个系统性风险"）。

## 5. 简历怎么写（两版对照）

### 5.1 现状版（达到 A 档即可用，4 条 bullet）

> **制造业经营分析数据仓库｜个人项目｜MySQL 8 + Python + FineBI**
> - 独立设计并实现 **源库 → ODS → DWD → DWS → ADS** 五层数仓，**7 库 46 表**，源库约 **270 万行 / 5 GB**，支撑 **7 张 FineBI 看板**。
> - ODS 层实现基于**水位表 + UPSERT** 的增量同步，支持重复执行与**断点续跑**；DWD/DWS/ADS 采用幂等全量重建，单次跑批约 **15 分钟**。
> - 自研**19 项数据质量断言**并接入调度器（跨层对账 DWD=DWS=ADS、容差 0.1%），**校验不通过则整批失败**，取代人工核对。
> - 主导 **12 条指标口径纠偏**（如营收剔除已取消订单、订单履约率分母改为已交付），并沉淀口径决策与故障复盘文档；曾定位并处置一次 **`table is full` 爆盘故障**（根因：MySQL binlog 未过期策略 + 巨型事务写 binlog + ODS 增量翻倍）。

### 5.2 达到 B 档后的升级版（加 2~3 条）

> - DWD 事实表按业务日期**分区**，改造为**按日增量写入**，单日回补耗时从 15 分钟降到 **X 分钟**（写实测数字）。
> - 对客户/产品维度实现 **SCD Type 2 拉链表**（`start_date / end_date / is_current`），支持历史订单还原下单时点的维度属性。
> - 将全量重建改为 **临时表 + `RENAME` 原子切换**，消除 `TRUNCATE` 隐式提交导致的"失败留空表"风险；补充 `pytest` 单测与 CI 门禁，`docker compose up` 一键复现环境。

### 5.3 写作纪律

- **量级必须真实**：270 万行就写 270 万行。面试官一定会追问量级，虚报必翻车。
- **每个数字都要能溯源**：写进简历的耗时/行数，面试前跑一次 `verify_data.py` 复核。
- **口径纠偏那一节是你最大的差异化**，要留一句引导面试官提问（就写"营收虚高约 20%"这种具体数字）。

## 6. 面试预案：5 个必答题（附当前答案与改进后答案）

| # | 面试官问 | 现在的答案 | 应给出的答案（补完后） |
|---|---|---|---|
| 1 | 上游日增 500 万行，怎么处理？ | 只能全量重算 | 分区 + 按日增量 + DWS 滚动窗口 |
| 2 | 客户改名，历史订单关联哪个名字？ | 全量重建，历史被覆盖 | SCD2 拉链表，按订单时点关联 |
